# P002 실제 인간 재개 지시와 잔여 검증 인계 — 2026-11-05

## 실제 지시와 범위

기존 plan 채팅의 실제 인간이 중지 이후 다음을 요청했다.

> 그럼 P002 시험의 plan/dev 중지를 재개하고 남은 검증도 마무리해줘.

이는 P002-20261029-A 시험에 남아 있는 plan/dev 양쪽 중지의 명시적 재개 근거다.
이전에 요구한 중지 유지보다 나중에 도착한 실제 인간 지시이며, 새 업무나 타 프로젝트의
중지를 해제하지 않는다. 각 실제 역할은 자기 checkpoint만 CLI로 재개하고 기존 이력을
보존한다. Dev는 기존 plan 채팅의 이 인간 원문을 직접 확인할 수 있다. 인간에게 동일한
재개 문장을 dev 채팅에도 복사하라고 다시 요구하지 않는다. 전달 메시지 자체를 인간
원문으로 취급하거나 인간이 별도의 dev-only 문장을 보냈다고 기록해서는 안 된다.

기존 P002 범위에서 남은 실제 세션 검증을 수행한다. P006/P007의 비동기 인계와 plan 질문
창구를 따른다. 실제 역할 간 검증 행동을 요청하는 인계는 허용된 S1–S5 시험 조율 및 기존
project 전달 위임의 범위이며, 단순 ACK ping이나 완료 감시 루프를 만들지 않는다.

## 확인한 기준선과 복구 경계

현재 커밋된 증거상 C1/C2는 PASS, S2는 PASS, S3 step 3까지 확인됐다. 마지막 fixture plan
commit은 `6d04038121ae96bb9ca6ab8ac4ad0761e94dfbc3`, fixture dev commit은
`86ba359b879fb69bb196484eb23966662381b8c4`다. 두 checkpoint는 PAUSED/all이며 두 번째
질문 `P901-decision-6ef38fbcb8c8.md`는 OPEN이다. 원래 판단 commit은
`c24af9db2772a73636ca4ebe003a92c708074c1d`, 원래 dev 채택 commit은
`d1d7b2a58639fb8d9c21ee64ab365577e80d49c3`이다.

이번 plan 읽기 점검에서 기존 임시 fixture의 main .git 디렉터리 일부는 남았으나 HEAD/config와
plan/dev .git 연결 파일이 없고 `git rev-parse`는 exit 128이었다. 이전 위치 매핑 파일도 없다.
남아 있는 objects 디렉터리만으로 객체/역사를 복구할 수 있다고 단정하지 않았다. 기존
불완전 경로에 git init/reset/덮어쓰기/정리를 하지 않는다. 실제 재개 CLI는 아직 실행하지 않았다.

Dev는 먼저 비파괴 inventory와 남은 파일/객체의 hash 및 기존 export를 보존한다. 별도 부재한
경로를 preview한 뒤 복구 사본에서 검사한다. 원래 객체를 복원할 수 있으면 commit/tree와
기존 export/hash를 대조하고 원래 plan/dev HEAD·정확 채택·중지·OPEN·runtime을 복원한다.
이것은 기존 시험 재개에 필요한 환경 복구이며 원본 임시 폴더나 다른 프로젝트 변경이 아니다.

원래 객체가 없거나 불완전하면 그 사실과 복구 가능 범위를 먼저 커밋해 plan에 판단을 요청한다.
새로 만든 commit을 역사적 SHA로 위조하거나 export를 새 실행 PASS로 취급하지 않는다.
불가피한 재구성은 별도 continuation ID/원본 연결/새 SHA 대응과 기대값을 plan이 검토한 뒤
진행한다. 최신 0.2.3을 역사적 0.2.0 fixture에 몰래 대체하지 않는다. 과거 S0/S1/S2 및
중지 기록·실패는 그대로 보존한다. 배포 main/훅/개인 스킬/제품 프로젝트는 변경하지 않는다.

## 역할별 다음 행동과 검증

1. 배포 dev는 이 검토가 포함된 정확 plan SHA를 안전한 경계에서 통합/채택한다. 기존 P007
   완료와 검토 원장은 보존한다. fixture의 exact adoption과 배포 저장소 adoption을 구별한다.
2. Dev가 복구 위치·상태·증거를 준비해 실제 plan에 전달한다. Plan은 경로/원래 HEAD·역할·
   writer와 자기 checkpoint를 직접 확인한 뒤 자기 역할에서 재개를 수행한다. Dev가 plan을
   대행하거나 plan이 dev checkpoint를 직접 편집하지 않는다.
3. 양쪽 재개는 이번 하나의 실제 인간 지시에 근거해 순차 처리할 수 있다. 가능하면 dev를
   먼저 재개하고 plan/all 및 OPEN이 남아 두 next=null인지 보존한 뒤, plan 재개 후 pauses=[]와
   OPEN에 따른 P901/P903 차단을 확인한다. 이는 같은 인간 양쪽 재개 지시의 단계적 실행이다.
   기존 S3 step 4/5의 '서로 다른 dev-only/plan 발언' 입력 형태와는 다름을 명시하고,
   별도 인간 발언을 만들지 않는다. 중간 상태 불변식과 실제 두 writer 검증은 완화하지 않는다.
4. 이번 지시는 현재 중지 해제이며 미래 새 pause/resume 발언의 사전 승인이 아니다.
   S3 step 6/7의 새로운 dev role 중지·중지 중 resolve-only·이후 재개가 필요해지는 실제
   단계에서는 plan이 사용자에게 필요한 입력만 한 번 요청한다. 이미 허용한 현재 재개를
   다시 묻지 않는다. 이 입력이 필요한 동안 해당 세부 검증은 대기하고 자동 PASS를 만들지 않는다.
5. 두 번째 OPEN은 재개만으로 resolve하지 않는다. 기존 검토된 답변/정확 SHA 채택과 S3의
   resolution-only 조건을 지킨다. S4 실제 양방향 전달은 PENDING/SENT/실제 수신 관찰을 각각
   보존한다. 실제 시험 인계에는 다음 fixture 행동·문서·SHA를 포함하고 receipt 추측은 금지한다.
6. S5에서 남은 fixture marker/의존 선택, 양쪽 guard/queue, 최신 배포 회귀와 결과 보고서를
   dev에 커밋한다. 실제 세션·복구/재구성·기계 회귀·미확인 입력 범위를 분리한다. C3–C5는
   해당 근거가 실제 충족됐을 때만 dev가 체크한다. 완료 결과/판단은 plan 검토로 전달한다.

## 준비 검토와 전달

검토 결론: 실제 현재 중지의 양쪽 재개 및 기존 P002 잔여 검증 진행은 승인 범위다.
환경 복구는 보존·원본 대조를 먼저 하고, 불완전 역사 재구성의 구체적 proposal은 후속 검토한다.
P002 완료 기준을 삭제하거나 S3 새 인간 입력을 자동 대체하지 않는다. 이 문서는 실행 완료,
실제 checkpoint 재개 또는 C3 PASS 증거가 아니다.

수신자: 확인된 기존 같은 프로젝트 dev 채팅. P002 원래 계약/준비 검토와 이 후속 검토를
함께 읽고 정확 SHA를 채택한다. 실제 도구 발송 결과만 SENT로 기록하고 plan은 완료를
기다리지 않고 응답을 끝낸다. 후속 plan fixture 행동/판단 요청은 안전한 경계에서 처리한다.
