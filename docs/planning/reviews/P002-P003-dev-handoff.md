## 수신 dev의 다음 행동

1. 상위와 dev AGENTS를 읽고 dev child에서 상태·역할·기존 채택 SHA·중지/결정을 확인한다.
   초기화의 읽기 전용 한정은 끝났으며 이 인간 위임에 따라 준비된 큐에 착수한다.
2. 메시지의 정확한 plan snapshot SHA를 통합한다. 기존 코드/진척/실패 로그를 보존하고
   `contract_guard.py adopt <전체-SHA> --review-reference
   docs/planning/reviews/P003-readiness.md`로 채택·커밋한다. P002 준비 검토도 함께 읽는다.
3. guard(worktree/index/HEAD)와 큐를 확인하고 P002의 환경 준비부터 시작한다.
   두 실제 채팅 참여·단계별 실제 인간 중지/재개 발언을 만들어 내지 않는다.
   필요한 실제 입력이 없으면 단계·근거·재개 지점을 기록한다. 모의 검사를 P002 PASS로 바꾸지 않는다.
4. P002가 실제 입력 대기라면 영향 범위가 허용하는 독립 P003 구현·회귀를 진행한다.
   installed 계약은 채택한 그대로 보존하고 배포 SKILL/references/assets/tests를 변경한다.
   실제 개인 설치/다른 프로젝트 적용/main·태그·릴리스/공유 훅 설치는 하지 않는다.
5. 실행 상태·추가 로그·실패/재검증·최신 PASS와 커밋된 증거를 함께 유지한다.
   standing 권한으로 기존 origin/dev에 정상 push한다. 사용자 중지는 명시 재개 전까지 유지한다.

## 수신 확인·전달 한계

dev는 자신의 응답에서 받은 SHA·문서·채택/착수 상태를 명시한다. 송신 plan은 읽기/대기 도구로
그 응답을 확인해 상태를 기록한다. 별도 역방향 메시지나 ACK에 대한 재전송을 요청하지 않는다.
전달 시도/도구 성공/SENT/수신 응답/ACK는 해당 시점에 별도 기록하며, 준비 문서 작성이나
push만으로 SENT/ACK를 만들지 않는다. 이 인계는 P002 검증의 시험 인계 결과를 대신하지 않는다.
