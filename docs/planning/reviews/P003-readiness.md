# P003 준비 검토 — 2026-10-29

판정: 준비 완료. P003을 dev 큐에 등록한다. 검토 담당은 이 plan 역할 채팅이다.
근거: 사용자 “하네스 관련 추가 ㄱ계획된 작업들도 쭉 진행해줘.” 요청과 기존 plan의
준비 검토·dev 등록 위임. 이번 범위는 접수된 P003의 계약 확정과 후속 배포 구현 준비다.

## 확정 범위

[P003 작업서](../plans/P003.md), [직접 인계·배포 계약](../P003-direct-handoff.md),
[최초 접수 검토](P003-request-review.md)를 함께 읽는다.

- 인간의 명시 지시/기존 위임과 호스트 도구가 있으면 수신자·커밋을 확인하고 직접 발송한다.
  재결재/사용자 복사 전달로 같은 승인된 행동을 되돌리지 않는 절차를 확정했다.
- 가능 여부 질문·채팅 생성·에이전트 메시지로 권한을 만들지 않는다. 결과 불명은 수신부터
  확인하고 단순 ACK의 중복·연쇄 전달을 방지한다. SENT/ACK/채택/완료를 분리한다.
- 코어 상태 머신/schema/CLI를 그대로 사용한다. 호스트 어댑터는 문서 절차이며 자동 전송기,
  새 플러그인 로더 또는 개인 스킬 강제 업그레이더를 구현하지 않는다.
- 배포 문서·패키지와 임시 설치의 정합성을 검증한다. 실제 개인 설치/다른 프로젝트 적용,
  main/태그/릴리스/원격 추가·전역 설정 변경은 포함하지 않는다.

## 채택과 실행 인계

이 검토·작업서·상세 계약·개정된 installed 계약/manifest가 포함된 단일 plan 커밋의
전체 40자리 SHA를 인수 기준으로 삼는다. dev는 기존 변경/실패/완료 로그를 보존하며
그 커밋을 통합하고 `contract_guard.py adopt <전체-SHA> --review-reference
docs/planning/reviews/P003-readiness.md`로 채택·커밋한 뒤 구현한다.
이 plan 채팅이 dev를 대신 통합·채택하거나 발송하지 않는다.

등록 검증 기대값은 P002/P003 모두 READY·미착수·0/5, next.plan=null, next.dev=P002다.
새 요구/결정/중지/인계 기록을 생성하지 않는다. P002 세 문서와 dev 커밋 진척은 보존한다.
plan의 기획 작업은 여기서 준비 완료이며 실제 배포 구현·검증 완료는 dev 증거로 판정한다.

## 등록 전 실제 확인

- P002/P003 parser·실행 정합성: 모두 준비 완료·미착수, 체크 0/5, 실행 로그 없음.
- P002의 작업서·상세 계약·준비 검토는 이전 커밋과 byte 단위 동일.
- 새/수정 기획 문서와 docs/process의 상대 링크 대상 존재 확인.
- 설치 manifest 15개 파일 hash 모두 일치. 옵션·version·관리 목록 유지, 관리 문서 세 hash만 변경.
- installed scripts·assets·훅·policy·AGENTS·VERSION은 기존 커밋과 동일.
- queue JSON: next.plan=null, next.dev=P002, P002/P003 모두 owner=dev/READY.
  새 요구/결정/중지/인계는 비어 있음. plan worktree guard와 diff 형식 검사 PASS.
- dev는 `d2b900713fb8aa7be8f1599c9ef92e5b401339dc`에서 clean이며 기존
  `65ab556479915b0bfab808a96cf524a219fe07e7` 채택 상태. plan이 대신 수정하지 않음.

이번 확인은 기획·운영 문서와 등록 정합성 검사다. 런타임 코드를 수정하지 않았으며
배포 회귀·실제 호스트 발송·개인 설치 활성화를 실행한 결과로 보고하지 않는다.
