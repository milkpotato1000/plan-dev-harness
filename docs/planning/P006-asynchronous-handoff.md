# P006 비동기 인계와 병렬 plan/dev 계약 — 2026-11-05

사용자 목적: 초기에는 큰 범위 기획, 개발 중에는 plan이 세부 P를 지속 준비하고 dev가 승인된
P를 우선순위대로 구현한다. Plan 채팅이 dev 완료 대기에 묶이면 안 된다. 이번 요청은 이
기능의 기획·직접 인계·구현·설치형 반영을 승인한다. 기존 작업·중지 상태는 보존한다.

## A. 단위별 순서와 세션 간 병렬성

각 P의 계획→검토→정확 채택→구현 순서는 유지한다. 서로 다른 P의 단계는 별도 plan/dev
채팅·worktree에서 겹칠 수 있다. 한 worktree에는 한 작성자만 둔다. P010 구현 중 plan은
사용자와 P011/P012를 논의·검토·등록할 수 있다. 승인된 목표 내에서 준비하며 업무 판단이나
새 목표를 발명하지 않는다. 초기화는 read/status/wait이고, 사용자 질문·초안의 좁은 범위도 유지한다.

같은 한 채팅이 양쪽을 순차 수행하는 fallback은 실제 병렬 세션이 아니다. Host capability와
메시지 주입/스케줄링 한계를 명시한다. 자동 daemon/heartbeat/스케줄러·새 채팅 생성은 추가하지 않는다.

## B. Plan 인계가 끝나는 지점

1. 준비된 P, 요구·검증·우선순위·의존성·범위/중지 경계를 검토하고 commit한다.
2. 해당 프로젝트 인간 위임과 기존 dev/host를 확인하고 전체 정확 SHA·문서·다음 행동을 보낸다.
3. 도구가 실제 성공하면 기존 이벤트를 SENT로 기록하고 commit/push 후 짧게 응답을 종료한다.
   ACK·채택·구현 완료를 기다리는 read/wait loop, sleep, 반복 상태 조회를 하지 않는다.
   Dev가 바쁘거나 응답하지 않아도 SENT 근거가 있으면 plan은 다음 기획에 사용 가능하다.
4. ACK는 자연스럽게 다음 plan 요청/상태 조회에서 실제 응답을 관찰했을 때만 추가한다.
   ACK가 없으면 SENT를 유지한다. 수신·채택·완료를 추정하거나 완료로 부풀리지 않는다.
5. 실패/불명은 실제 상태와 근거를 보존하고 알려 준다. 불명을 SENT로 만들거나 맹목 재전송하지 않는다.
   도구/권한이 없으면 file handoff PENDING이다. 수신 확인이 필요한 다음 조회에서만 재확인한다.
   원인이 실제 권한/대상/결정 부족일 때만 필요한 질문을 한다. 인계 완료를 대신하는 긴 대기는 없다.

정상 안내: ‘Pxxx 기획·검토와 dev 전달을 마쳤습니다. Dev에서 구현을 진행하며 이 plan에서는
다음 기획을 계속할 수 있습니다.’ 실제 전달 성공·구현 미완료를 구별한다. 실패 시 성공 안내는 금지한다.
이 P006의 plan 발신 턴 자체도 SENT를 기록하면 종료하며 dev 완료/ACK 확인을 기다리지 않는다.

## C. Dev의 수신·busy 처리와 실행 경계

- 수신 자체는 현재 P를 취소/재시작하거나 미커밋을 버릴 권한이 아니다. 메시지를 대기할
  검토된 인계로 취급하고 현재 승인 작업과 실패·증거·log를 보존한다. Host가 즉시 메시지를
  주입하더라도 의미적으로 현재 P를 임의 선점하지 않는다. 강제 프로세스 중단은 하지 않는다.
- 현재 작업을 완료하거나 안전하게 checkpoint/commit한 경계에서 전달 문서와 정확 SHA를
  검토·통합·채택·commit하고 guard/큐를 확인한다. 사용자가 지정한 긴급 중지는 즉시 우선한다.
- 다음 P는 그때 채택한 계약 내 준비·우선순위·선행·권한·결정/중지 상태로 고른다.
  단지 메시지 도착 순서대로 실행하거나 검토되지 않은 최신 plan tip을 자동 채택하지 않는다.
  여러 인계가 누적되면 포함 관계·각 검토 범위를 확인하고 보존적으로 처리한다.
- 새 P 전달은 현재 채택된 P의 요구/완료 조건을 소급 변경하지 않는다. 변경된 계약은 별도
  검토·정확 채택 후 적용한다. 스코프·검증을 낮추거나 완료 체크/실패 이력을 삭제하지 않는다.
- Dev 완료/결정 요청은 자기 채팅과 커밋된 증거에 남긴다. 수신 메시지가 역방향/연쇄 전송
  권한을 만들지 않는다. Plan이 자동으로 완료 감시를 맡는 구조로 되돌리지 않는다.

## D. 중지와 결정 대기 보존

명시 중지·OPEN 결정은 그대로다. 업무 인계/ACK/새 버전/시간 경과는 resume/resolve가 아니다.
중지 중에는 실제 사용자 범위가 허용한 기록·상태 확인만 하고 착수 요청을 하지 않는다.
Legacy scope-less/all PAUSED는 양쪽, 명시 role scope는 해당 역할에 적용한다.
OPEN 미분류는 기존 보수적 dev 차단을 유지한다. 범위를 줄이려면 기존 plan 검토·채택을 거친다.
독립 기획은 해당 plan이 중지되지 않았고 실제 승인 범위일 때 계속한다. 병렬성을 이유로 차단을
축소하지 않는다. P002 fixture 중지는 독립 P006의 구현을 중지시키지 않으며 P002는 재개하지 않는다.

## E. 구현·배포 범위와 소유권

Source VERSION0.2.2, source SKILL/references/usage/direct-handoff, assets instructions/process/templates,
Codex/Claude prompts, bootstrap/install 생성 진입점, README와 필요한 tests를 정합하게 갱신한다.
기존 event schema/guard/CLI를 유지하는 지침 patch가 우선이며 새 runtime/스키마 설계가 필요하면
immutable intake로 후속 plan 검토를 받는다. 큐/훅은 계속 조회/검사만 하며 전송하지 않는다.

현재 plan 소유 실제 AGENTS·agent-workflow·workflow-controls·work-queue·handoff-template 및
outer/reconstruction 지침에는 본 계약의 비동기 규칙을 먼저 적용한다. managed manifest는
변경된 관리 문서 hash만 갱신하고 기존 파일목록/옵션·version0.2.1·runtime을 유지한다.
이는 검토된 지침 통합이며 local managed 설치 전체를0.2.2로 갱신했다고 표시하지 않는다.
Dev는 exact adopt 후 이 지침을 사용하고 배포 source/assets를 구현한다. 보호 파일의 추가
변경은 승인 baseline 밖에서 자가 승인하지 않는다. Source/개인 설치0.2.2와 local managed
version0.2.1의 계층 차이를 검증 문서에 정확히 남긴다.

사용자가 설치형 반영을 요청했으므로 현재 로드된 Codex 스킬 사본은 실제 경로·VERSION·확장·
중복 discovery를 조사하고 백업·검증된 새 payload로 안전하게 전환한다. 기존 P004 추가파일과
UI metadata·개인 확장을 보존한다. 설치용과 같은 이름의 프로젝트 일상 스킬을 교체하지 않는다.
다른 Claude 개인 설치는 발견됐다는 이유로 변경하지 않고, Claude 배포 패키지는 임시 설치로 검증한다.
권한 차단은 정상 escalation으로 처리하며 실패를 성공으로 표시하지 않는다. 다른 세 제품 프로젝트
일괄 재설치·main/tag/release/PR 병합·원격 추가·인증/DB/외부 서비스 변경은 이번 범위 밖이다.
기존 non-force plan/dev push 권한만 사용한다.

## F. 독립 기대값과 증거

- N1: 전송 성공 후 ACK/완료가 없어도 SENT를 commit하고 plan 턴이 반환한다. 완료 대기 호출 없음.
- N2: Dev가 P010 중이어도 plan이 독립 P011/P012를 준비·등록·전달할 수 있다. 현재 dev 계약/작업 불변.
- N3: 새 인계는 busy P를 임의 중단하지 않는다. 안전한 경계 뒤 exact adoption, 다음 우선순위/선행 적용.
- N4: ACK가 나중에 관찰되면 기존 event만 증거로 갱신하고 중복 발송/역방향 ACK loop 없음.
- N5: 전송 실패·불명·권한/host 부재를 구분해 PENDING/이전상태 유지, 가짜 SENT/재전송 없음.
- N6: 중지 role/all/legacy, OPEN 결정, 사용자 긴급 중지가 병렬 인계로 해제되지 않는다.
- N7: 현재 P 변경 제안/미검토 최신 tip/여러 누적 인계가 현재 승인 범위를 자동 변경하지 않는다.
- N8: 새/재개 세션과 Codex/Claude 설치형·bootstrap/upgrade에 같은 규칙이 도달하고 역할/단독 작성권 유지.
- N9: 사용자 요청 없는 새 목표/P 자동 발명·bootstrap 착수·메시징 grant 확대·자동 감시 없음.
- N10: P005 결과/기존 실패·작업·P002 PAUSED/OPEN·main·hook 구성·확장 사본 보존.

Fixture P010~P012는 임시 저장소에만 만든다. 실제 제품 카드를 시험용으로 재등록하지 않는다.
테스트는 문구 존재 검사를 넘어 두 worktree의 채택 고정·P추가·다음선택·pause/decision 보존,
실패/불명 전달 adapter 기대값을 확인한다. Host 지원과 모델 정책은 별도 검토 표로 남긴다.
실제 새 사용자 발언을 테스트 전제로 강요하지 않는다. 이 P006 발신 턴은 실제 send/SENT 뒤
종료한 근거만 제공하며 아직 없는 두 번째 사용자 입력/새 모델 세션 준수를 PASS라 하지 않는다.
전체 unittest, 패키지 독립 설치/업그레이드, guard worktree/index/HEAD, 큐, 실제 loaded 파일/버전/hash를
확인한다. 최신 실제 근거만 P006 체크와 append-only 로그에 반영하고 실패도 보존한다.
