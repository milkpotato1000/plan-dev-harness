# P007 사용자 검토·결정의 plan 단일 창구 — 2026-11-05

## 사용자 의도와 근거

사용자 보고: 한 프로젝트에서 같은 완료 확인을 dev와 plan이 각각 질문했다. 사용자는 보통
plan에서 결과를 보며 추가 기획하고, dev는 코드 조회 등 필요할 때만 방문한다. Dev는 일반
구현·검증을 사용자 개입 없이 진행하고 판단이 필요한 사항을 plan으로 인계한다.
보고 프로젝트의 최근 기록에서 양쪽이 같은 UI 확인을 반영한 흔적은 읽었으나, 질문 원문의
완전한 대조나 모든 원인 재현을 했다고 주장하지 않는다. 비공개 프로젝트·경로·원문은 배포 Git에 넣지 않는다.

## 1. 역할과 질문 소유권

- Dev: 정확 채택된 P 구현·자동 검증·기존 범위 기술적 수정·증거/결과 생성. 단순 완료마다
  ‘확인해 주세요/다음 진행할까요’를 묻지 않는다. 결과 검토·사람 확인·의미/범위 결정은 plan에 인계한다.
- Plan: 결과와 실패·한계를 읽고 파일·화면을 실제 가능한 도구로 열어 검토한다. 자동/직접 검증으로
  해결할 내용은 먼저 확인한다. 사용자 취향·업무 의미·사람에게 명시된 승인만 plan에서 한 번 묻는다.
  기존 계약/합의·위임 내 판단은 plan이 근거를 남겨 결정한다. 부족한 권한/사업 판단을 발명하지 않는다.
- 사용자가 dev에서 코드를 보거나 직접 질문하면 dev는 그 요청에 답할 수 있다. 그 답변을 plan과
  공유해 같은 질문을 재발행하지 않는다. 플랫폼의 필수 사용자 승인/안전 차단은 정상 절차를 따른다.
  다른 세션을 통해 승인 차단을 우회하거나 인간 관찰을 에이전트 관찰로 대체하지 않는다.

## 2. 결과 검토와 질문의 식별·보존

Dev는 일반 결과/검토 인계에 최소 다음을 커밋한다: P/criterion, 목적, 검토할 파일/URL·결과의
정확 commit과 material version/hash, 실제 검증/실패/미확인, 확인 종류(UI/내용/정책 등),
질문 또는 필요한 결정, 추천/선택지·영향, 관련 기존 request key/질문·답변의 식별 가능한 출처,
다음 안전 행동·차단 범위. 인증정보나 대화 전체는 포함하지 않는다.

공통 request key는 프로젝트 내 P/확인 항목 + 확인 종류/범위 + 검토 artifact의 식별/실질 버전에서
안정적으로 정한다. 단순 메시지 ID·새 인계 commit만을 의미적 중복 방지 key로 쓰지 않는다.
같은 review를 가리키는 여러 전달 event/재시작도 공통 key에 연결한다. 예시 파일 경로:
`docs/feedback/dev/reviews/<key>.md`(dev 원본),
`docs/planning/reviews/user-reviews/<key>.md`(plan 검토/질문/결정 원장).
Source 요청·기존 답변/실패는 덮거나 지우지 않고 후속 기록과 연결한다. 기존 immutable intake는 그대로다.

Plan은 질문 전에 공통 원장과 이미 커밋된 사용자 확인 근거를 읽는다. 같은 범위가 답변 대기면
질문을 다시 띄우지 않고 기존 질문과 연결한다. 이미 답변된 범위는 식별 가능한 실제 사용자
출처·대상 version/hash·범위를 확인해 재사용한다. 기존 dev에서 받은 유효한 답변도 인정하되
에이전트 ‘사용자가 승인했다’ 한 줄만으로 인간 승인을 창작하지 않는다.

UI 동작 확인은 정답/사업 내용 승인과 다르다. 같은 파일이라도 별도 의미의 판단이면 무엇이
이미 확인됐고 무엇을 새로 묻는지 분명히 설명한다. 실질적으로 달라진 artifact에는 기존 승인을
자동 이월하지 않는다. 단순 timestamp/새 전송 등 실질 변경 없는 경우에는 대응 근거를 남겨
기존 확인을 재사용할 수 있다. 승인 범위를 넓히는 근거로 쓸 수는 없다.

공통 key와 기록 규약은 에이전트 의무와 검증 대상이다. 기존 transport event의 SHA별 중복
억제를 사용자 질문의 의미적 중복 억제라고 과장하지 않는다. Host 전체 UI를 기계적으로 봉쇄하는
새 보안 guard라고 주장하지 않는다. 최소한의 protocol/template과 stateful 검증으로 구현한다.
새 schema/CLI나 runtime 보호 변경이 필요하면 격리 proposal과 후속 plan 검토를 먼저 받는다.

## 3. 실제 결과 열기와 검토

Plan은 dev의 커밋된 결과를 git show/dev evidence로 읽고, 공유되는 파일/안전한 독립 사본을
해당 viewer/browser 도구로 연다. 실제 사용한 artifact version/hash와 검사 범위를 기록한다.
Dev worktree에 들어가 편집·생성/서버 실행·제품 코드를 실행하지 않는다. 실행/뷰 서버가 필요하면
그 준비는 dev가 승인 범위에서 수행한다. Plan은 준비된 read-only 결과를 본다.
파일 링크를 사용자에게 제공할 수 있고, 화면을 실제 못 열었으면 링크 제공/내용 읽기와 실제
시각 확인을 구별한다. 도구가 차단되면 정상 권한/대체 검토를 쓰고 우회하거나 검토 PASS를 꾸미지 않는다.
실제 사람 확인이 필수인 기준은 plan의 도구 관찰로 자동 충족시키지 않는다.

검토에서 새 요구가 나오면 기존 계약·P에 해당하는지 먼저 판단한다. 기존 범위 수정은 해당 P와
근거를 연결해 dev로 넘기고, 새 범위는 immutable intake/계획·준비·정확 채택을 따른다.
Plan이 dev 구현을 대신하거나 사람이 답하지 않은 사항을 승인하지 않는다.

## 4. 결정·대기·완료의 구분

- 선택적 결과 검토: dev는 코드/검증 완료를 기록하고 plan에 전달한 뒤 다른 독립 승인 작업을 진행한다.
  자동 검증 PASS, 사용자 검토 대기, 사용자 승인, 구현 완료는 서로 다른 사실이다.
- 필수 사람 확인이 P 완료 기준이면: 그 criterion은 미완료로 유지한다. 해당 P는 기존 허용된 실행
  BLOCKED/로그로 대기 근거를 남기고, 의존하지 않는 승인 작업은 기존 규칙이 허용할 때 진행한다.
  UI 확인만 필요한 대기를 전역 critical PLAN_DECISION으로 바꾸지 않는다.
- 의미/권한/정확성/필수 검증을 결정할 수 없는 critical 이슈: 기존 PLAN_DECISION/OPEN을 커밋해
  plan에 전달한다. 기존 legacy 미분류 all 차단을 임의 축소하지 않는다. Plan의 검토·분류·정확 채택
  뒤에만 기존 규칙대로 scope/resolve를 적용한다. 병렬 기획과 사용자 중지를 구분한다.
- Plan이 결정을 확정하면 근거·대상 request key·실제 사용자 답변 범위를 커밋하고 필요한 P/준비 검토를
  갱신한다. Dev는 그 정확 plan을 통합/adopt한 뒤에만 구현/decision resolve/사람 기준 체크에 반영한다.
  Plan에서 한 번 질문하고 답을 받았다는 이유만으로 아직 채택되지 않은 dev 계약을 바꾸지 않는다.

## 5. 직접 전달 권한과 비동기 운영

현재 실제 사용자 요청은 이 하네스 프로젝트에서 기존 dev→기존 plan의 결과 검토/결정 요청 전달과,
plan→dev의 검토된 결정/작업 인계를 허용하는 인간 근거다. 별도 project-local 위임 문서에 남긴다.
이것은 ACK 회신·무관한 상태 ping·새 채팅·타 프로젝트·다른 수신자·서비스 쓰기·중지 재개 허가가 아니다.
배포 패키지는 이 프로토콜을 제공하되 설치 자체가 다른 프로젝트의 인간 메시징 위임을 만들지 않는다.
각 프로젝트에서 실제 인간 지시/기존 위임을 확인하고 제공되는 host 도구를 사용한다.

일반 검토 결과에는 기존 WORK_READY(target plan, 목적은 결과 검토), critical에는 기존
DECISION_REQUEST를 사용하고 문서에 용도를 명시할 수 있다. 새 event 종류/schema를 발명할 필요 없다.
명시 권한·host·수신자가 있으면 커밋된 문서·정확 SHA·공통 request key를 전달하고 실제 SENT를 기록한다.
SENT 뒤 ACK/결정/완료 대기 loop를 하지 않는다. Busy plan도 자기 승인 작업의 안전한 경계에서 접수하고
결과 검토를 후속 기획과 함께 처리한다. 임의로 현재 턴을 취소하거나 기존 답변 대기를 새 질문으로 대체하지 않는다.

필수 판단 대기 시 해당 P/영향 범위만 기존 규칙으로 대기한다. 사용자는 dev를 열거나 문장을 복사해
전달할 필요가 없어야 한다. 권한·도구가 없으면 durable pending file과 plan의 자연스러운 다음 조회로
접수하며 전달/자동 깨우기 성공을 꾸미지 않는다. 미전송을 이유로 같은 사용자 질문을 dev에 중복 발행하지 않는다.
플랫폼 자체의 필수 승인·긴급 위험 알림 등 실제 필요한 사용자 개입은 숨기지 않는다.

## 6. 구현과 배포 경계

P006을 먼저 구현·검증·commit한 안전한 경계 뒤 P007 exact adopt한다. 진행 중인 source/assets와
개인 스킬 전환을 취소하거나 미커밋을 버리지 않는다. 기존 P006 동작·실패 기록을 보존한다.
Source/설치형0.2.3로 SKILL/references/role prompts·bootstrap/new session·assets/instructions/process/
검토 template·README 및 관련 tests를 정합하게 갱신한다. 현재 로드된 Codex 사본은0.2.2 전환 완료
확인 후 조사·백업·확장/UI metadata 보존해 안전 갱신한다. Claude 패키지는 독립 임시 설치로 검증한다.
같은 이름의 프로젝트 일상 skill/임의 Claude 개인 설치는 바꾸지 않는다.

Plan 소유 actual installed governance와 outer 지침을 먼저 적용한다. manifest는 관리 문서 hash만
갱신하고 version0.2.1/옵션/runtime은 유지한다. source/개인 설치0.2.3과 local managed marker의 계층을
구별한다. 보호 파일의 추가 구현은 자가 승인하지 않는다. 설치 기능만으로 타 제품 프로젝트를
일괄 재설치하거나 현재 보고 프로젝트의 제품 기준/승인/코드/실행 기록을 고치지 않는다.
Main/tag/release/PR merge·외부 서비스·인증·DB·대량 메시징·P002 resume/resolve는 제외한다.
기존 정상 plan/dev push 권한만 사용한다. Plan은 인계 SENT 후 응답을 끝내 다음 기획에 사용 가능하다.

## 7. 독립 검증 기대값

M1 dev 결과 생성→커밋 증거/plan 인계, dev 질문0·plan 질문최대1. 완료마다 사용자 개입 없음.
M2 plan이 실제 artifact를 열고 검사한 범위를 기록; 못 연 경우 실제 관찰로 표시하지 않음.
M3 중복 transport event·새 commit·재시작·동일 key 대기/답변 상태에서 같은 질문 재발행 없음.
M4 기존 dev 사용자 확인을 동일 hash/범위로 재사용; 인간 출처 불명은 승인 창작 없음.
M5 UI와 내용/정책 범위 분리; 실질 변경 artifact는 재검토, 비실질 변경의 재사용은 근거 필요.
M6 기존 합의로 plan 결정→commit→exact adopt→실행; 실제 사용자 판단은 plan에서만 질문.
M7 선택적 검토는 독립 큐 유지; 필수 사람 criterion 미완료; critical OPEN/legacy와 scope 채택 보존.
M8 busy plan/dev·P006 실행/실패·single writer·비동기 SENT 종료·ACK 지연·중지 유지.
M9 actual grant에 따른 dev→plan 전달과 설치 자체 무권한/host 부재의 durable fallback, 중복 질문 없음.
M10 사용자가 dev에서 직접 코드 질문·확인 응답한 경우 응답은 허용하고 결과를 같은 key에 연결.
M11 정규 필수 승인/안전 차단을 다른 세션으로 우회하지 않음, 새 채팅/ACK ping-pong 없음.
M12 Codex/Claude 독립 설치/upgrade/bootstrap·활성 사본 hash·전체 회귀·P002/main 보존.

가상 fixture로 두 역할·같은 key·사용자 응답1회·버전 변경/재개·독립 큐를 stateful 검증한다.
같은 문구가 있는지만 검사해서 실제 사용자 질문 중복 방지가 증명됐다고 하지 않는다. 실제 host
관찰·모델 정책 검토·시뮬레이션·기계 테스트를 구분하며 새 사용자 발언을 테스트 의무로 강요하지 않는다.
