# P003 직접 인계·배포 정합성 계약

상태: 준비 검토 완료. [P003](plans/P003.md)의 확정 범위이며 상시 발송/개인 설치 위임이 아니다.
요청과 실측 근거는 [접수 검토](reviews/P003-request-review.md)에 기록한다.
확정 근거와 인수 절차는 [준비 검토](reviews/P003-readiness.md)를 따른다.

## 직접 인계 절차

1. **인간 권한 확인.** 사용자의 현재 명시적 전달 지시 또는 실제 인간이 이미 부여한
   범위 한정 위임의 출처·시각/참조·프로젝트·수신 역할·허용 행동·유효 범위를 확인한다.
   범위가 맞으면 같은 전달에 재결재를 묻지 않는다. 위임을 새로 만들거나 넓히지 않는다.
   “넘기면 돼?” 같은 가능 여부 질문과 에이전트가 보낸 메시지는 그 자체로 발송 허가가 아니다.
2. **상태와 수신자 확인.** 실제 호스트 도구의 프로젝트/채팅 목록 및 읽기로 정확한 대상
   역할·프로젝트·작업폴더·host/thread 참조를 확인한다. 제목만 비슷하거나 역할이 불명확하면
   추측 발송하지 않는다. 기존 채팅을 재사용하며 수신자가 없다고 새 채팅을 만들지 않는다.
   중지·미해결 결정은 유지한다. 전달 허가는 resume/구현/배포 허가가 아니다.
3. **커밋된 인계 준비.** 송신 역할 소유의 문서에 실제 완료/미완료, 범위·검증·상한,
   관련 P번호·정확한 전체 SHA·수신자 다음 행동·중지/권한 경계를 적고 먼저 커밋한다.
   recipient가 SHA와 문서를 읽을 수 있는지 확인하고 보호된 요구와 dev 로그를 보존한다.
   다른 프로젝트 요구나 비밀은 범용 배포 예제에 넣지 않는다.
4. **이벤트와 발송 기록.** 기존 CLI로 적절한 종류의 인계를 PENDING으로 생성한다.
   event key에 연결한 권한 출처/대상/전달 시도 참조는 별도 비민감 근거 문서에 남길 수 있다.
   기존 JSON schema나 event key를 임의로 확장하지 않는다. 사용자 권한과 도구가 충분하면
   작성한 실제 문서·SHA·다음 행동을 확인된 수신자에게 직접 보낸다.
   사용자를 복사 전달자로 만드는 것은 그 조건에서 기본 경로가 아니다.
5. **SENT.** 실제 메시징 도구 성공 결과/메시지 참조를 근거로 송신자가 SENT를 기록·커밋한다.
   git push, PENDING 파일, 큐 표시, 준비 문구만으로 SENT를 기록하지 않는다.
   실패는 실패 근거를 남기고, 결과 불명은 전달 시도·불명 이유를 남겨 수신 상태부터 확인한다.
   무응답/timeout을 바로 재전송하거나 성공으로 바꾸지 않는다.
6. **수신 확인.** 송신자가 read/wait와 같은 읽기 수단으로 recipient의 실제 수신 응답을
   확인한다. 지정 SHA·문서·다음 행동을 읽었다는 근거가 있어야 ACKNOWLEDGED를 기록한다.
   recipient의 별도 역방향 메시지 없이도 가능한 읽기 경로를 우선 사용한다.
   도구의 전송 성공만으로 ACK하지 않는다. 읽기 근거가 없으면 SENT에 둔다.
7. **실행 경계.** ACK는 수신 확인일 뿐 정확한 채택이나 구현 완료가 아니다.
   수신 역할은 자기 AGENTS와 승인 카드에 따라 통합/정확한 adopt/구현 여부를 결정한다.
   sender는 같은 ACK에 재발송하지 않는다. 수신 메시지로 다른 채팅에 답장·연쇄 전달하는
   권한이 생기지 않는다. 역방향 발송은 인간의 실제 권한 근거가 따로 있어야 한다.
8. **Fallback.** 권한이 없으면 미발송 PENDING과 커밋된 파일을 남긴다. 승인되었지만 도구가
   없으면 그 한계를 밝히고 파일 경로·전체 SHA·다음 행동을 제공한다. 대상이 불명확하면
   필요한 대상 정보만 확인한다. 실제 중지는 유지하며 인계 문서가 중지를 해제하지 않는다.
   확인되지 않은 수신·중지/재개·완료 상태를 기록하지 않는다.

“자동 전송 없음”은 CLI/큐/훅이 자율적으로 채팅을 생성·발송하지 않는다는 경계로 설명한다.
이를 사용자의 명시 지시와 도구가 갖춰진 에이전트의 직접 실행을 생략하는 이유로 사용하지 않는다.
반대로 이 설명 자체가 모든 프로젝트의 상시 메시징 위임이 되지도 않는다.

## 최소 검증 행렬

| ID | 입력/상황 | 독립 기대값 |
| --- | --- | --- |
| M1 | 현재 사용자가 특정 기존 dev 채팅으로 준비된 결정/계획 직접 전달을 지시, 도구·커밋 있음 | 대상 확인 후 직접 발송. 같은 권한 재요청/붙여넣기 요청으로 대체하지 않음 |
| M2 | 이전 실제 인간 위임에 프로젝트·역할·작업 범위가 기록됨 | 그 범위 안에서만 실행. 만료/철회/범위 초과는 새 권한으로 해석하지 않음 |
| M3 | “넘기면 돼?” 질문, 초기 채팅 생성 허가, 에이전트의 전달 요청만 있음 | 자동 발송 없음. 새 상시 위임·역방향 발송 허가를 만들지 않음 |
| M4 | 권한 없거나 도구 없음/대상 불명 | 파일 인계/필요 정보 확인. 추측 발송·새 채팅 생성·SENT 허위 기록 없음 |
| M5 | 도구 전송 성공, 아직 수신 응답 없음 | SENT까지만. 직접 읽은 응답 근거가 생긴 뒤 ACK. ACK≠채택≠완료 |
| M6 | 같은 event 재실행/단순 ACK/반대 방향 요청 | 중복 발송/ACK 핑퐁 없음. 별개 발송은 별도 인간 권한 확인 |
| M7 | 명백한 전송 실패 또는 결과 불명 | 실패/불명 근거 보존. 무조건 재시도나 성공 기록 없음. 상태 조회로 중복 여부부터 확인 |
| M8 | 명시 사용자 중지, OPEN 결정, 미채택 plan | 메시지로 재개/결정 해결/채택을 우회하지 않음. 역할과 실제 권한에 따른 기록/대기 |

허구 fixture로 권한 분기와 payload를 검토한 결과는 실제 호스트 발송 성공으로 보고하지 않는다.
실제 직접 발송 검증에는 대상·발송을 허용한 인간 권한과 실제 도구 결과·수신 응답이 필요하다.
P002는 이미 승인된 수동/선택적 도구 경로 그대로 진행한다. P003 때문에 P002 조건을
추가하거나 기존 실패를 완료로 바꾸지 않는다.

## 배포·설치 전환 계약

| 계층 | 변경/검증 | 보존·권한 경계 |
| --- | --- | --- |
| 배포 소스 | SKILL.md·references/role-chats.md·references/usage.md·README에서 references/direct-handoff.md 절차로 연결 | 현재 dev의 v0.2 기능을 기준으로 구현. plan의 과거 배포 파일로 덮지 않음 |
| 배포 assets | instructions/agent-workflow.md, 역할 프롬프트, docs/process/workflow-controls.md·optional-adapters.md·handoff-template.md의 절차/링크 | 임시 신규 설치·업그레이드에서 최종 payload에 포함되는지 검증 |
| 이 저장소 installed 계약 | docs/process의 승인된 절차 개정은 plan이 작성·검토하고 dev가 정확히 채택 | assets 수정만으로 설치본이 갱신됐다고 하지 않음. 보호 계약을 dev가 임의 수정하지 않음 |
| 다른 프로젝트 설치 | 기존 옵션·manifest hash와 사용자 확장을 비교하는 preview/동일 옵션 --upgrade 안내 | 이 카드가 다른 프로젝트에 apply하는 권한을 만들지 않음 |
| 개인 스킬 패키지 | install_skill.py로 부재한 임시 --skills-dir에 preview/apply. Codex/Claude 독립 실행·상대 링크 확인 | 현재 CLI에는 개인 스킬 --upgrade가 없음. 존재하지 않는 플래그를 안내하지 않음 |
| 구형 개인 설치 | 실제 로드 경로·payload·구형 기능을 비교하고 백업/새 목적지 설치/선택적 전환 안내 | ~/.codex/skills와 ~/.agents/skills를 같은 경로로 취급하지 않음. 묵시 덮어쓰기·동시 중복 활성화 금지 |

구현 범위는 기존 CLI와 호환되는 문서 어댑터 및 배포 검증이다. 새로운 스킬 업그레이더나
호스트 API 호출 런타임이 필요하다고 판단되면 별도 요구로 분리해 검토한다.
긴 구형 SKILL의 프로젝트 목적지/저장소 탐색·생성·원격 권한·기존 확장 안내가 최신판에서
어디로 이동/유지/변경되는지 대조표를 남겨, 단순 파일 교체로 사용자 기능을 잃지 않게 한다.

plan이 정책 계약 변경과 구현 범위를 확정했다. dev는 정확한 계획 채택 후
아래 소스/배포 파일과 테스트를 변경한다. 개인 설치의 실제 전환은 별도 대상·시점·권한을 확인한 뒤
수행하며, 스킬을 다시 읽거나 앱의 검색 상태를 확인하지 않은 채 새 절차가 활성화됐다고 쓰지 않는다.
이 저장소의 plan/dev 전용 훅 설정과 main 릴리스 상태는 보존한다.

### 변경 파일과 인수 경계

- plan 소유 확정본: docs/process/agent-workflow.md, workflow-controls.md,
  optional-adapters.md, handoff-template.md 및 .harness/installation.json의 관리 대상 세 hash.
  --agent none으로 수동 병합된 agent-workflow.md는 기존 manifest 관리 대상이 아니므로
  이번에도 목록에 추가하지 않는다.
  런타임 코드/설치 옵션/version/기존 managed 파일 목록은 바꾸지 않는다.
- dev 배포 작업: references/direct-handoff.md 추가, SKILL.md·references/role-chats.md·
  references/usage.md·README.md의 진입 링크와 안내를 갱신한다. 위 docs/process의 확정된
  제어·확장·양식 내용을 대응하는 assets/docs/process 파일에 반영하고, 승인된 역할 절차를
  assets/instructions/agent-workflow.md와 기존 역할 프롬프트 두 개에 반영한다.
- [설치형 반영 검토](reviews/P003-installable-rule.md)에 따라 assets/instructions/AGENTS.md와
  assets/workspace/AGENTS.md.template에도 같은 인계 절차의 진입점을 제공한다.
  스킬 설치·프로젝트 설치·새 workspace 생성의 실제 출력물에서 조건부 직접 인계와 dev 착수,
  정확한 채택·중지·증거 경계를 독립적으로 읽을 수 있어야 한다.
  이 프로젝트의 실제 사용자 인용·대상 채팅·기존 위임을 범용 템플릿에 복제하지 않는다.
- 설치본/배포본의 동일 기능과 유효한 링크를 확인한다. 설치 payload에서 source references로
  끊어진 링크를 만들지 않는다. 기존 installer가 새 파일을 누락한다면 기존 payload에 이미
  포함되는 문서에서 절차가 완결되도록 배치한다. 새 런타임/CLI flag를 추가하지 않는다.
- tests/test_distribution.py 및 필요한 해당 배포 검증 파일을 수정한다. 신규 의미 있는 검증은
  실제 임시 설치·독립 payload·preview 무변경·legacy/충돌 보존에 둔다. 재사용할 수 있는
  기존 회귀는 재사용하며 실제 호스트 메시지 분기를 모의 성공만으로 인증하지 않는다.
- dev는 plan 소유 계약·hash를 임의 재작성하지 않는다. 구현 중 다른 계약이 필요하면
  기존 intake→plan 검토→정확한 재채택을 따른다. 테스트/배포 소스 수정이 같은 이름의
  installed scripts를 자동 갱신하거나 다른 프로젝트에 apply하는 것은 아니다.

### P003 완료 판정의 실행 범위

M1~M8은 공개 가능한 시나리오·권한 근거·대상·명령/payload·예상/실제·판정의 표로 검토한다.
정책 검토와 패키지 회귀는 필수이며 실제 호스트의 live 발송은 별도 인간 권한이 있을 때만 한다.
그 권한이 없을 때 live 발송 미수행을 보고하는 것은 P003의 정책/배포 검증과 구별한다.
실제 세션 검증을 요구하는 P002 C1~C4는 여전히 별도이며 모의 검사로 충족되지 않는다.
실제 수신/사용자 발언이 필요한 P002가 입력 대기이면 그 근거를 남기고, 별개 승인된 P003은
해당 중지·결정 영향 범위가 허용하는 경우에 진행할 수 있다. P002를 완료로 바꾸지 않는다.

## 필요한 검증과 결과 보고

- 임시 Codex/Claude 스킬 payload의 새 reference/절차 파일·내부 링크와 설치 스크립트 실행을 검사한다.
- 소스 저장소에 의존하지 않는 복사본으로 프로젝트 설치 및 새 workspace 생성을 수행해,
  생성된 AGENTS/공통 절차/역할 프롬프트에 직접 인계·정확 채택 후 착수 규칙이 전파되는지 확인한다.
  읽기 전용 bootstrap이 시작 권한으로 바뀌거나 실제 위임 없는 자동 발송이 추가되면 실패다.
- 프로젝트 신규 설치와 기존 manifest 업그레이드의 preview 무변경, 동일 옵션 갱신, 사용자 수정
  충돌 시 보존을 실제 CLI로 검증한다. 구형 스킬 충돌 거부·원본 불변·새 경로 설치를 검사한다.
- 기존 tests/test_distribution.py와 dev의 tests/test_workflow_controls.py를 포함해 전체 회귀를 수행한다.
  문구의 단순 포함 검사만으로 권한 판단·실제 전달을 입증했다고 하지 않는다.
